  <name>Task 2: Key hierarchy (deriveMasterKek + recovery wrap) (TDD)</name>
  <files>

  <action>
**RED:** Tests for the hierarchy from CRYPTO-STACK §3 + §8:
1. `deriveMasterKek({ password, secretKey, email, argon2Params })` returns a 32-byte key.
   - Sub-step contract per §3: `master_seed = HKDF-SHA256(ikm = secret_key, salt = email_lowercased, info = "simplevault.v1.master_seed")`; then `master_KEK = Argon2id(password, salt = master_seed XOR user_argon_salt, params)`. The fn must accept `userArgonSalt` too.
2. Different passwords → different KEKs. Different secretKeys → different KEKs. Different emails → different KEKs.
3. `deriveRecoveryKek({ mnemonic, userId })` returns a 32-byte key:
   - `recovery_seed = mnemonicToSeed(mnemonic)` then `HKDF-SHA256(ikm=seed, salt=userId, info="simplevault.v1.recovery_kek", L=32)`.
4. `wrapKey(plaintextKey, wrappingKey, aad)` and `unwrapKey(wrapped, wrappingKey, aad)` round-trip via the AEAD module.
5. End-to-end: generate `master_DEK = randombytes_buf(32)`; wrap with `master_KEK`; unwrap; bytes-equal.
6. Recovery round-trip: wrap `master_DEK` with `recovery_KEK`; unwrap with mnemonic-derived KEK; bytes-equal.
7. AAD downgrade defence: change argon2 params bytes in the AAD; unwrap throws (tag mismatch).

Commit RED.

**GREEN:** Implement `key-hierarchy.ts` using:
- `@noble/hashes/hkdf` + `sha256` for HKDF.
- Plan 02's `argon2id.deriveKey` for the Argon2id step.
- Plan 02's `aead.encrypt`/`decrypt` for wrap/unwrap.

Define a canonical AAD encoding: `version_byte (0x01) || argon2_params_serialised (12 bytes: m_be32 || t_be32 || p_be32) || context_id_bytes (variable, e.g. user_id UUID bytes)`. Export `encodeAad(params, contextId)` so the API layer can reproduce it byte-for-byte.

Commit GREEN.

**REFACTOR:** Re-export through both barrels. Add a parity test that imports both `browser` and `node` and asserts the function set + types match.
