# Phase 03 — 2FA (WebAuthn + TOTP) + session management UI (Index + Wave Map)

**Goal (must be TRUE):** A user can enroll a passkey AND a TOTP credential, log in with master+secret_key+2FA, see their active sessions, and remotely log out a session.

> **Builds on Phase 02.** The auth surface (signup, login, refresh, logout, /me, JWT, sessions table, throttler, audit-events) is FROZEN per `02-PHASE-SUMMARY.md`. Phase 03 EXTENDS, never replaces. Specifically: JWT shape `{sub, sid, fam, iat, exp}` + header `{alg:"HS256", kid:"primary"}` gains a `epoch` claim (REQ-AUTH-004 deferred from Phase 02); `__Host-refresh` cookie + same-origin under `pass.runadev.com` continues to hold; AAD scheme `sv:user-*:v1|` + per-user binder `SHA256(lower(email))` extends with `sv:user-totp:v1|` for the TOTP secret wrap; the 11-action `AuditAction` enum extends to add 2FA / session actions WITHOUT bumping `v`.

## Goal-backward truths

For the goal to be TRUE, all of the following must be observable:

1. `POST /2fa/webauthn/begin-register` (auth required) returns a server-generated 32-byte challenge (`base64url`), `rp.id = WEBAUTHN_RP_ID`, `rp.name = "SimpleVault"`, `user.{id, name, displayName}`, `pubKeyCredParams = [-7, -257]` (ES256 + RS256), `authenticatorSelection.userVerification = "required"`, `attestation = "none"`, plus a server-side `webauthn_challenge` row written with TTL=120s. Replaying the same challenge after consume → 400 `WEBAUTHN_CHALLENGE_INVALID`.
2. `POST /2fa/webauthn/finish-register` (auth required) verifies attestation via `@simplewebauthn/server` against the matching `webauthn_challenge` row (consumed atomically), persists `(user_id, credential_id, public_key, counter, transports[], aaguid, name, created_at)` in `webauthn_credentials`, returns `{id, name}`. After success, `GET /2fa/methods` lists the new method.
3. `POST /2fa/webauthn/begin-auth` accepts a 1FA-completed step-up token (issued by `/auth/login` only when the user has ≥1 active 2FA method — see Truth 8), returns `allowCredentials = user.webauthn_credentials.map(c => ({id, type:"public-key", transports}))` + a fresh `challenge` row, TTL=120s. Pre-1FA challenge requests → 400.
4. `POST /2fa/webauthn/finish-auth` verifies the assertion, asserts `counter > stored.counter` (rejects clones — emits `auth.2fa.webauthn.auth.fail` with reason `counter_regression`), updates `counter`, consumes the challenge atomically, then promotes the step-up token to a fully-authenticated access JWT + `__Host-refresh` cookie identical to a Phase-02 successful login.
5. `POST /2fa/totp/begin-register` (auth required) generates a 20-byte TOTP secret client-side; the **server NEVER sees plaintext** — the client posts the secret already wrapped under `master_DEK` with AAD label `"sv:user-totp:v1|"` + per-user binder `SHA256(lower(email))`, returns `{provisioningUrl, qrPng}` for the user to register in their authenticator (the URL is computed client-side; the server only stores the wrapped blob and a fresh issuance nonce that the finish step consumes).
6. `POST /2fa/totp/finish-register` accepts a 6-digit code; client-side decrypts the wrapped secret with `master_DEK`, runs RFC 6238 (SHA-1, 30s, ±1 step) locally to verify, then posts `{wrappedSecret, encryptedSecretAad, name, lastUsedStep: <verifiedStep>}` and the server INSERTs `totp_credentials(user_id, wrapped_secret, name, last_used_step, created_at)`. Last-step replay guard initialised. Returns `{id, name}`.
7. `POST /2fa/totp/verify` accepts a step-up token + 6-digit code: client decrypts, computes locally, posts `{credentialId, candidateStep}`. Server: `UPDATE totp_credentials SET last_used_step = $cs WHERE id = $cid AND last_used_step < $cs RETURNING *`. Zero rows updated → 401 `AUTH_2FA_TOTP_REPLAY` (the same step or earlier was already used). One row updated → promote step-up token to fully-authenticated session.
8. `POST /auth/login` (Phase 02) extension: when the verified user has ≥1 active 2FA method, the response is NOT a normal `{accessToken, refresh-cookie, wrapped material}` 200 — it is a **2FA challenge response**: `{stepUpToken: "<jwt>", twoFa: {webauthnAvailable: bool, totpAvailable: bool}}` (HTTP 200, body shape distinct from 1FA-only). The step-up JWT is signed with the same `JWT_SECRET` but carries `{sub, purpose:"2fa-stepup", epoch}` (NO `sid`/`fam`), `exp = iat + 120`, and only `/2fa/*` accept it. A user with zero active 2FA methods continues to receive a full session (Phase-02 behaviour preserved).
9. `GET /2fa/methods` (auth required) lists the user's active 2FA: `[{id, kind:"webauthn"|"totp", name, createdAt, lastUsedAt}]`. Order: webauthn first, then totp, then by createdAt asc. NEVER returns secret material, public-key bytes, raw counters, or wrapped blobs.
10. `DELETE /2fa/methods/:id` (auth required) removes the named method. **2FA-removal guard**: if removing this method would leave the user with 0 active 2FA AND `userHasSharedVaultDependency(userId)` returns true, reject 409 `AUTH_2FA_REMOVAL_BLOCKED`. The dependency function is feature-flagged: in Phase 03 it always returns `false` (no shared vaults exist yet), but its implementation site + integration test are in place so Phase 07 only has to flip the flag (explicit hand-off).
11. `GET /sessions` (auth required) lists ALL non-revoked rows for the current user from `user_sessions`: `[{id, createdAt, lastUsedAt, current: bool, userAgentFamily, ipHashB64Prefix:"<6 chars>" }]`. **`ipHashB64Prefix`** is the first 6 chars of the base64-encoded ip-hash — enough for the user to recognise "same network" without leaking the full hash to the browser. `current: true` for the row whose `id === req.user.sessionId`.
12. `DELETE /sessions/:id` (auth required) family-revokes the session (same `revokeFamilyByToken` semantics as logout, but parameterised by `sessionId` instead of cookie token-hash). Cannot delete a row that doesn't belong to `req.user.id` (404, NOT 403 — anti-enumeration). Bumps the targeted user's `session_epoch`, cutting all access tokens for that user within ≤ next-request latency.
13. `POST /sessions/revoke-all` (auth required) family-revokes EVERY non-revoked row for `req.user.id` AND bumps `users.session_epoch`. Returns 200 `{revokedCount}`. The current request's access token is invalidated as soon as the next request lands (epoch check fails). The current refresh cookie is also invalidated.
14. **Session-epoch claim landed.** `users.session_epoch INT NOT NULL DEFAULT 0`. JWT payload gains `epoch: <int>`. `JwtAuthGuard` verifies `payload.epoch === user.session_epoch` (single Redis-cached read per request, TTL 60s, busted on any write to the column). Mismatched epoch → 401 `AUTH_SESSION_REVOKED`. Adds <2 ms p99 to authed requests on cache hit (verified in Plan 04 verify step). Closes Phase-02 deferred REQ-AUTH-004 + AT-5 leaf A residual.
15. **2FA-required guard for `vault.*`**: a NestJS guard `Require2FAGuard` queries `(SELECT COUNT(*) FROM webauthn_credentials WHERE user_id=$1) + (SELECT COUNT(*) FROM totp_credentials WHERE user_id=$1) >= 1`. Wired into the (yet-to-exist Phase 07) `vault.create` and `vault.join` routes via decorator metadata. **Phase 03 ships the guard + a stub controller route `POST /vault/_2fa-guard-probe` (gated behind `EXPOSE_TEST_ROUTES=1`)** so the guard is e2e-tested before Phase 07 lands; production builds DO NOT register the probe route.
16. Web `/settings/security` lists 2FA methods, has "Add passkey" + "Add authenticator app" buttons that drive the begin/finish endpoints, shows a remove button per method (with the removal-guard 409 surfaced as a clear error), and prominently labels passkey as **PREFERRED — phishing-resistant** with TOTP labelled "phone-only — vulnerable to phishing".
17. Web `/settings/sessions` lists active sessions with `current` row pinned at the top and visually distinct, has a "Sign out" button per other-row (calls `DELETE /sessions/:id`), has a "Sign out everywhere except this device" CTA that calls `POST /sessions/revoke-all` and immediately wipes local key-store + redirects to `/login`.
18. **Throttler ordering FIXED (FINDING-0021 fold-in).** `JwtAuthGuard` is registered as `APP_GUARD` (with a `@Public()` decorator opt-out for `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/params`, `/invite/redeem`, `/health`) so it runs BEFORE the global `SimpleVaultThrottlerGuard`. New user-keyed ceilings (`2fa-register-user`, `2fa-verify-user`, `sessions-list-user`, `sessions-revoke-user`, `sessions-revoke-all-user`) all key correctly off `req.user.id`. `/me` user-keyed limit becomes correct as a side effect (closes FINDING-0021).
19. **Email length cap landed (FINDING-0017 fold-in).** `users.email` + `invite_codes.email` migrate to `varchar(254)` (RFC 5321 ceiling); `LoginSchema.email`, `SignupSchema.email`, `InviteRedeemSchema.email` all gain `.max(254)`. **Throttler `login-email` keying caps via `sha256(email).slice(0,16)`** (closes FINDING-0022 by the same fix).
20. The Phase-02 12 truths still hold (regression-tested via the existing E2E suite). New E2E specs cover: webauthn-register (using `@simplewebauthn/server`'s test-helpers + a virtual authenticator), totp-register-and-verify (with deterministic RFC 6238 vectors), session-list-and-revoke, revoke-all-killing-current-token-via-epoch.

## Key links (where this most likely breaks)

1. **WebAuthn `RP ID` mismatch.** Production RP ID = `pass.runadev.com` (apex domain — CONFIRMED by operator decision in 03-INDEX). RP ID is bound into every credential at registration; if `WEBAUTHN_RP_ID` env drifts on prod (e.g. operator types `www.pass.runadev.com`), every previously-registered passkey BREAKS — they cannot be re-derived. RP ID change is a data-migration event. Plan 03 (webauthn API) verifies env at boot via fail-fast + DOCUMENTS this in the runbook.
2. **WebAuthn challenge nonce uniqueness + atomic consume.** Challenge rows are written with TTL=120s + a unique-index on `(user_id, kind:'register'|'auth')`. The finish endpoint MUST consume atomically: `DELETE FROM webauthn_challenges WHERE id = $1 RETURNING challenge` — if zero rows return, 400. NEVER look up + then delete in two statements (TOCTOU race; double-redemption opens replay).
3. **TOTP secret encryption is browser-only.** The `master_DEK` lives in the in-memory `keyStore` on the web client; it MUST NEVER touch the API. The `begin-register` endpoint emits ONLY the *issuance nonce*; the actual secret is generated, displayed (QR + provisioning URL), wrapped, and posted in `finish-register`. Test: `grep -r "totp" apps/api/src` should find ZERO references to `master_DEK`, `master_kek`, or anything that could mean "we have the secret server-side". The server stores the wrapped blob + an opaque AAD blob — that's it.
4. **TOTP last-step replay guard.** `last_used_step` MUST advance via `UPDATE ... WHERE last_used_step < $cs RETURNING *` (atomic compare-and-swap — Postgres provides this for free). Two attackers running the same code simultaneously: one wins, one gets zero rows → 401. Drift tolerance ±1 step means an attacker who captures step N can NOT also use step N+1 if the legit user already burned N+1; ensure `verify` accepts only `cs >= last_used_step + 1` after drift normalisation, NOT `cs >= last_used_step`.
5. **Step-up token ↔ access JWT separation.** The step-up token has `purpose:"2fa-stepup"` and `exp = iat + 120` (env-tunable `STEP_UP_TOKEN_TTL`, default 120s). It MUST NOT be accepted by `JwtAuthGuard` for any non-`/2fa/*` route. Implementation: `JwtAuthGuard` rejects any token where `payload.purpose !== undefined`; `Require2FAStepUpGuard` is the dual that ONLY accepts `purpose:"2fa-stepup"`. Mixing these guards = either bypass or deadlock.
6. **Session-epoch storage choice.** RECOMMENDED: column on `users` (`session_epoch INT NOT NULL DEFAULT 0`); JWT carries it; `JwtAuthGuard` validates against a Redis cache of `users.session_epoch` (TTL 60s, busted on every write to the column from `revoke-all` or `DELETE /sessions/:id`). Alternative considered: per-session-id revocation set in Redis (no JWT change). Picked the column approach because it gives a fully self-contained primitive (no Redis = still safe to deploy locally) and the cost is one numeric column comparison after the existing `users` row hot-cache hit. **OPERATOR DECISION SURFACED — confirm before execution.**
7. **2FA removal guard vs Phase 07 dependency.** `userHasSharedVaultDependency(userId)` lives in `apps/api/src/twofa/two-fa-guard.ts`; in Phase 03 it returns `false` unconditionally with a `// TODO(phase-07): replace with vault_members.count(...)` comment AND a registered counter for an integration test that simulates the Phase-07-flipped behaviour by stubbing the function. Tests assert: (a) baseline always allows removal, (b) when stub returns true + user has 1 method, removal returns 409 — guarantees Phase 07 only has to swap the implementation.
8. **2FA-required guard for `vault.*`.** Same pattern: an `EXPOSE_TEST_ROUTES=1` build flag exposes `POST /vault/_2fa-guard-probe` so we can E2E-test the guard without the actual vault module existing. PROD container build sets this to undefined → route is absent. Phase 07 deletes the probe route and registers the real one.
9. **`@simplewebauthn/server` v10 vs v11.** Library is on v11+ as of Jan 2026; pin to `^11.0.0` exactly. Ceremony helpers: `generateRegistrationOptions`, `verifyRegistrationResponse`, `generateAuthenticationOptions`, `verifyAuthenticationResponse`. RP ID + origin must be passed explicitly (defaults are not safe). In Plan 02 (webauthn API) the verify call MUST pass `expectedOrigin: WEBAUTHN_ORIGIN` (= `https://pass.runadev.com` in prod, `http://localhost:3000` in dev) — origin mismatch means every assertion fails 100% silently for the user.
10. **Throttler ordering fix (FINDING-0021).** Moving `JwtAuthGuard` to APP_GUARD reorders the entire guard chain. Every existing `@UseGuards(JwtAuthGuard)` decorator becomes redundant (and remains harmless). Every endpoint NOT meant to require auth must declare `@Public()` — the migration must enumerate them: `/health`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/params`, `/invite/redeem`, `/2fa/webauthn/begin-auth`, `/2fa/webauthn/finish-auth`, `/2fa/totp/verify`. Anything missed = 401 on every request to that route. Plan 09 has an explicit enumeration step + grep verification.
11. **Email length cap migration (FINDING-0017).** `text -> varchar(254)` on `users.email` and `invite_codes.email` is a destructive type change but for our cardinality (≤50 rows) trivially safe. Drizzle migration must be expand-then-contract-in-single-step: `ALTER COLUMN email TYPE varchar(254) USING substring(email,1,254)` is idempotent if no row has email > 254 (verifier query at start of migration: `SELECT email FROM users WHERE length(email) > 254` → must be empty before applying).
12. **Phishing-without-WebAuthn (THREAT-MODEL §17 HIGH).** UX label is part of the threat-control. The web `/settings/security` page MUST present passkey as primary CTA (button styling, ordering) AND TOTP must carry a copy block "Authenticator-app codes can be entered into a phishing site. Use a passkey when possible." The auditor will check copy + ordering — not just function.
13. **Cypress + virtual authenticator.** Use Chrome DevTools Protocol via `cy.task('addVirtualAuthenticator', ...)` to create a software authenticator before the spec, drop it after. The `@simplewebauthn/server` test helper builds a paired test client; alternative is an in-spec authenticator emulator. Phase 12 will verify e2e coverage matches the threat-model leaves.

## Operator decisions surfaced (REQUIRED before `/gsd:execute-phase 3`)

The following six decisions have proposed defaults; operator must confirm OR override before executor runs. Defaults are documented; overriding only requires editing the relevant Plan + this INDEX before kick-off.

1. **WebAuthn RP ID = `pass.runadev.com`** (apex; same as the prod origin host). Apex (NOT `www.`) because the operator is deploying without a www-subdomain, and changing RP ID later is a data-migration event (every passkey re-registration). Confirm.
2. **WebAuthn user verification = `required`** (per REQ-2FA-001). Consequence: registration/auth requires the user to provide a local biometric/PIN. PASS-WITH-CONCERNS would flag `preferred` as too lax for SimpleVault's threat model. Confirm.
3. **WebAuthn attestation = `none`**. Operator-issued invites at ≤50 user scale do not benefit from authenticator-attestation policies (no organisational allow-list of authenticator vendors); raising this to `direct` adds privacy concerns + UX friction without a corresponding security gain at this scale. Phase 13 may revisit. Confirm.
4. **Session-epoch column on `users`** (vs Redis-only revocation set). Picked because it gives a self-contained primitive that survives Redis outage and adds <2 ms p99 to authed requests. Confirm — this is the load-bearing call that resolves REQ-AUTH-004.
5. **Step-up token TTL = 120 seconds** (env `STEP_UP_TOKEN_TTL`). Long enough for a user to retrieve their phone + open authenticator + type 6 digits; short enough that a stolen step-up token is useless before the user finishes the 2FA ceremony. Confirm.
6. **`EXPOSE_TEST_ROUTES` build flag for the 2FA-required-guard probe.** Phase 07 will replace with the real `vault.*` routes; until then the guard is testable via `POST /vault/_2fa-guard-probe`. Default in production: undefined (route absent). Confirm — alternative is to skip e2e coverage of this guard until Phase 07.
