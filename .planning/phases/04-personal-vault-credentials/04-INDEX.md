# Phase 04 — Personal vault: credentials (Index + Wave Map)

**Goal (must be TRUE):** A logged-in user can create, edit, view, and delete credentials in their personal vault. All payload data is encrypted client-side; the server only sees ciphertext + minimal metadata (`id`, `vault_id`, `version`, `updated_at`). Password generator (charset + EFF-large passphrase), `zxcvbn-ts` strength meter, in-vault reuse detection, and 15-minute idle auto-lock all work end-to-end.

> **Builds on Phase 03.** The auth + crypto + 2FA + sessions surface is FROZEN per `02-PHASE-SUMMARY.md` + `03-INDEX.md`. Phase 04 EXTENDS, never replaces. Specifically: AAD scheme `sv:user-*:v1|` extends with a per-blob `sv:vault-credential:v1|` label binding `(vault_id ‖ credential_id ‖ version)` (REQ-CRYPTO-001 contract); `master_DEK` lives in the in-memory `keyStore` populated by `/login` (Phase 02 carry-over §"Phase 04") and is the key under which credential blobs are wrapped; `JwtAuthGuard` (APP_GUARD, FINDING-0021 fold-in from Phase 03) + `epoch` claim guard every credential route; the `Require2FAGuard` stub probe route from Phase 03 (Plan 03-07) is **DELETED** and replaced by the real personal-vault routes (no 2FA gate on personal vault per REQ-2FA-003 — 2FA is mandatory only for shared vaults, Phase 07); the 11-action `AuditAction` enum extends with `credential.{create,update,delete,view}` WITHOUT bumping `v` (Phase 02 §"AuditEvent v1 shape FROZEN"); throttler ceilings extend with `vault-read-user`, `credential-write-user` (user-keyed; both consumable now that FINDING-0021 landed in Phase 03).

## Goal-backward truths

For the goal to be TRUE, all of the following must be observable:

1. `GET /vault/personal` (auth required) returns `{id: <uuid>, ownerUserId: <uuid>, createdAt, updatedAt}` for the caller's auto-created personal vault. Auto-creation is a Phase-02 signup-time side effect (Plan 04-01 backfills existing users via Drizzle migration; new users get the row inserted in the same transaction as `users` insert in `signup.service.ts`). Cross-user lookup is impossible by construction (no `:id` parameter).
2. `POST /credentials` (auth required) accepts `{vaultId: <uuid>, ciphertext: bytea, nonce: bytea(24), aadParamsJson: <string>, version: 1}`; server validates `vaultId` belongs to caller (`SELECT 1 FROM vaults WHERE id=$1 AND owner_user_id=$2`), inserts row, returns `{id, vaultId, version: 1, updatedAt}`. Server NEVER inspects ciphertext content; rejects bodies > 64 KiB (FINDING-0015 fold-in opt-in cap; credential blob ceiling).
3. `GET /credentials/:id` (auth required) returns `{id, vaultId, version, ciphertext, nonce, aadParamsJson, updatedAt}`. Cross-user / not-found returns uniform 404 `CREDENTIAL_NOT_FOUND` (anti-enumeration; same posture as `DELETE /sessions/:id` Phase 03 Truth 12).
4. `PATCH /credentials/:id` (auth required) accepts `{ciphertext, nonce, aadParamsJson, version: <expected_current>}` and runs an **atomic CAS update**: `UPDATE credentials SET ciphertext=$1, nonce=$2, aad_params_json=$3, version=$4+1, updated_at=now() WHERE id=$5 AND vault_id IN (SELECT id FROM vaults WHERE owner_user_id=$6) AND version=$4 RETURNING *`. Zero rows updated → 409 `CREDENTIAL_VERSION_CONFLICT` (the AAD-bound version is the anti-rollback primitive; concurrent edits OR replay of an old PATCH both lose).
5. `DELETE /credentials/:id` (auth required) hard-deletes the row (no soft-delete in v1 — REQ-VAULT spec). Cross-user / not-found returns uniform 404. Returns 204.
6. **AAD per-credential binder.** Client builds `aad = "sv:vault-credential:v1|" ‖ canonicalJson({vault_id, credential_id, version, kdf_params})` and supplies it to `aead.encrypt`/`decrypt`. The server stores `aad_params_json` (the canonical-JSON portion) so the client can re-derive AAD on read; the label prefix is a CONSTANT and lives in `apps/web/src/lib/crypto/aad-labels.ts` (extends the Phase-02 module — closes FINDING-0026 by example, not by fix; see Forwarded findings disposition).
7. **Server cannot decrypt.** Two grep gates run in CI (Plan 04-12 verify):
   (a) `grep -rn "master_DEK\|master_dek\|master_kek" apps/api/src` finds ZERO matches except the existing pino redaction wildcard (FINDING-0041 carry-over).
   (b) `grep -rn "ciphertext\|aead\|decrypt" apps/api/src/credentials apps/api/src/vault` finds ZERO calls into `@simplevault/crypto`'s encrypt/decrypt. The credentials module imports DB primitives only.
8. **Reuse detection is browser-only.** On `/vault` mount, the client decrypts every credential blob, computes `sha256(password)` for each, and stores them in a `Set<string>` in React state. Save flows display "this password is reused in N other items" without blocking save. Server has zero awareness of password equality. Test (Plan 04-09 verify): `grep -rn "sha256\|reuse" apps/api/src/credentials` returns ZERO.
9. **Password generator.** `apps/web/src/lib/passwords/generator.ts` exports `generatePassword({length, lower, upper, digits, symbols})` and `generatePassphrase({wordCount, separator})`. Length range 8–128 (REQ-VAULT-003); passphrase 3–10 words. Entropy source = `crypto.getRandomValues` ONLY (no `Math.random`); rejection-sampling for unbiased per-class selection. Passphrase wordlist is the EFF large list (7776 words, vendored under `apps/web/src/lib/passwords/eff-large.ts` with the SHA-256 of the upstream file pinned in a comment + a unit test asserting `wordlist.length === 7776` and `sha256(wordlist.join("\n"))` matches).
10. **zxcvbn-ts strength meter.** Live meter in credential editor; score 0–4 + crack-time annotation. `zxcvbn-ts` and its `@zxcvbn-ts/language-en` dictionaries are vendored, lazy-loaded via dynamic `import()` to avoid bloating the initial JS bundle (Aceternity-card list view loads first; meter loads only on `/credential/new` + `/credential/[id]`).
11. **Auto-lock — 15 min idle.** A client-only watchdog (`useAutoLock` hook) tracks `pointermove`, `keydown`, `visibilitychange`, and the most recent `/me` activity timestamp. After 15 minutes (env-tunable `AUTO_LOCK_IDLE_MS`, default 900000) without a tracked event, it calls `keyStore.wipe()`, redirects to `/login`, and clears React state holding decrypted blobs. Server is NOT notified (auto-lock is a client invariant only — REQ-WEBSEC-007). Sessions remain valid server-side until refresh-token rotation expires.
12. **Password history (encrypted, in-blob).** When a credential's password changes via PATCH, the client appends `{password: <prev>, changedAt}` to a `history[]` array INSIDE the plaintext payload, capped at 10 entries (oldest evicted). Old plaintext NEVER leaves the encrypted blob. Server only sees the new ciphertext (different nonce, bumped version). REQ-VAULT-006.
13. **Favorites flag.** `is_favorite: bool` lives INSIDE the encrypted payload (REQ-VAULT-011). NOT a server-readable column. UI sort/pin happens client-side after decrypt.
14. **`/vault` list view (mobile-first).** Aceternity card-grid (vendored under `apps/web/src/components/aceternity/` per Key Link 7); lists all credentials decrypted client-side. Search box filters by `name` + `url[]` host; favorites pinned at top. Empty-state CTA → `/credential/new`.
15. **`/credential/new` + `/credential/[id]`.** Form fields per REQ-VAULT-002: `name` (required), `url[]` (multi), `username`, `password` (with generator + meter + reveal toggle + copy-with-30s-clipboard-clear hook from Phase 12 stub — landed but inert until CSP final), `notes`, `custom_fields[{name, value, hidden}]`. Submit → encrypt → `POST` (or atomic CAS `PATCH`) → optimistic local-state update.
16. **Throttler ceilings extended.** New user-keyed ceilings: `vault-read-user` (300/15min — matches REQ-RATELIMIT-006), `credential-write-user` (60/min/user — write-burst cap, prevents runaway clients). All key off `req.user.id` correctly post-FINDING-0021 fix. Documented next to existing ceilings in `apps/api/src/common/throttler.config.ts`.
17. **Audit-events extended (v1 shape preserved).** `AuditAction` enum gains `credential.create`, `credential.update`, `credential.delete`, `credential.view` (the last for read-traceability — emitted on `GET /credentials/:id`, NOT on `GET /vault/personal` to avoid log-amplification on list page-loads). `data` payload carries `{credentialId, vaultId, version}` — NEVER ciphertext, AAD, or any decrypted field.
18. **Input validation (`.strict()`).** Every new DTO uses `.strict()` Zod schemas (closes FINDING-0014 contagion); `aadParamsJson` validated as length-bounded JSON (max 2 KiB); `ciphertext` + `nonce` validated as `Uint8Array` of correct shape (`nonce.length === 24`).
19. **Access-control invariants.** `vaults` table has unique constraint `(owner_user_id, kind='personal')` so each user has exactly ONE personal vault. Every credential read/write joins through `vaults.owner_user_id = req.user.id` — IDOR is impossible at SQL level (not just guard level).
20. **Cypress E2E green** for: create → list → view → edit (version bumps) → delete; reuse detection surfaces correctly; generator produces in-bounds output for 1000 trials; auto-lock fires at the configured interval (Cypress clock-control); CAS-conflict on PATCH returns 409; 404 on cross-user ID; 64-KiB body cap on POST returns 413.

## Key links (where this most likely breaks)

1. **AAD per-credential binder MUST include `(vault_id ‖ credential_id ‖ version)`.** Missing any of the three opens a distinct attack: omit `vault_id` → cross-vault substitution (Phase 07 surface); omit `credential_id` → cross-credential substitution within a vault; omit `version` → rollback (server replays an old ciphertext under the same `id`). The label literal `"sv:vault-credential:v1|"` is FROZEN at this point and lives in `aad-labels.ts` — extending the v-suffix later is a data-migration event (mirrors the Phase-02 lesson on the user-* labels). Plan 04-02 lands the literal + a parity test.
2. **`version` is the AAD anti-rollback primitive.** PATCH MUST run the atomic CAS (`WHERE version = $current`) AND the new ciphertext's AAD MUST encode the **incremented** version. If the client encrypts with the OLD version + the server bumps the column on insert, the next read will fail AEAD-tag because the stored `aad_params_json.version` mismatches. The protocol: client computes `newVersion = currentVersion + 1`, encrypts with AAD including `newVersion`, sends `{ciphertext, nonce, aadParamsJson, version: currentVersion}` (the `version` field is the CAS-witness, not the new value). Server CAS: `... SET version = currentVersion + 1 WHERE version = currentVersion`. Diverging from this protocol = silent decrypt failures on next read.
3. **2FA-required guard MUST NOT be wired onto personal-vault routes.** REQ-2FA-003: 2FA is OPTIONAL for personal vault use, MANDATORY for shared. Phase 03 left a stub probe route under `/vault/_2fa-guard-probe`; Plan 04-01 DELETES that route and registers the real `/vault/personal` + `/credentials/*` routes WITHOUT the `Require2FAGuard` decorator. The guard implementation stays (Phase 07 will wire it onto `/shared-vaults/*`); only the probe goes. Verify-step grep: `grep -rn "Require2FAGuard\|_2fa-guard-probe" apps/api/src/vault apps/api/src/credentials` returns ZERO.
4. **Auto-lock is a CLIENT invariant.** Server has no concept of "locked"; `keyStore.wipe()` is a browser-RAM event. The server-side session remains valid until refresh-token expiry (Phase 02 contract). Implication: auto-lock + browser-tab-close is NOT a "remote logout" — for that, the user calls `POST /sessions/revoke-all` (Phase 03). The runbook MUST document this distinction; otherwise users will misinterpret "I locked the vault" as "all my sessions are dead".
5. **Reuse detection is INFORMATIONAL and BROWSER-ONLY.** Per REQ-VAULT-005: detection happens via a local `Set<sha256(password)>` computed AFTER decrypt; the UI surfaces a count next to the strength meter. It does NOT block save (a user may legitimately rotate from one strong reused password to another while transitioning); it does NOT report to the server; it does NOT sync across devices (each browser computes its own set on `/vault` mount). Phase 07 expansion (shared vaults) will need to decide: extend reuse detection across ALL vaults the user can decrypt, or keep it per-vault — flagged for Phase 07 INDEX, not solved here.
6. **Password history rotation must NEVER leak old plaintext outside the encrypted blob.** The full `history[]` lives INSIDE the plaintext payload; on PATCH, the client decrypts, mutates `history`, re-encrypts under a fresh nonce + bumped version, sends. There is NO "old password" column, NO "previous ciphertext" stash on the server. Implication: on key rotation (Phase 11 master-password change), all credentials get re-wrapped — history rides along inside each blob.
7. **Aceternity components MUST be vendored, not pulled at runtime.** Aceternity-UI ships components by copy-paste from their docs (their license model + supply-chain posture). Vendor under `apps/web/src/components/aceternity/` with the source URL + commit SHA in a header comment per file. CSP `connect-src 'self'` (REQ-WEBSEC-001) would block any runtime CDN fetch anyway, but vendoring also pins supply-chain (no NPM-hijack vector via an `aceternity-ui` package).
8. **CSP and the libsodium WASM.** The libsodium WASM blob is bundled into the web app's static assets; it loads via same-origin `'self'` already permitted by REQ-WEBSEC-001. NO `wasm-unsafe-eval` directive needed (libsodium-wrappers-sumo uses `WebAssembly.instantiate(buffer)`, not `eval`). Plan 04-12 verify includes a Cypress assertion that `/vault` loads cleanly under the FINAL Phase-12 CSP (forward-test; failure here is a Phase-12 problem, not Phase-04, but caught here).
9. **`AuditAction` enum extension does not bump v.** Phase 02 froze `AuditEvent v1`. Adding `credential.{create,update,delete,view}` to the enum is additive — Phase 10's hash-chain ingest treats unknown action types as opaque-but-chainable. The enum lives in `packages/shared/src/audit/audit-event.ts`; extension preserves alphabetical order + numeric stability for any downstream `instanceof`/integer-encoding consumers.
10. **`vaults` table backfill on existing users.** Phase 02 closed with N existing users (operator + early invitees) having no `vaults` row. The Plan 04-01 migration MUST run a one-shot `INSERT INTO vaults (owner_user_id, kind) SELECT id, 'personal' FROM users WHERE NOT EXISTS (SELECT 1 FROM vaults WHERE owner_user_id = users.id AND kind = 'personal')` AS PART OF the migration (idempotent). Forgetting this = every existing user gets `VAULT_NOT_FOUND` on their first `/vault/personal` call after deploy.
11. **Body-size cap on `POST/PATCH /credentials`.** FINDING-0015 (Phase 02 OPEN, Low) flagged that the global Express body limit was never explicitly set. Phase 04 introduces the FIRST endpoints that legitimately want > 64 KiB envelopes (a credential with 10 custom fields + 10 password-history entries can approach this). Decision: explicit per-route opt-in to `app.useBodyParser('json', { limit: '64kb' })` for `/credentials/*` (folds FINDING-0015 partially); per-route override raises to a documented `CREDENTIAL_BODY_MAX_BYTES` (default 64 KiB; ceiling 128 KiB enforced at controller level). Above ceiling → 413 `CREDENTIAL_BODY_TOO_LARGE`.
12. **`zxcvbn-ts` dictionaries are large.** Full English dictionary is ~700 KiB ungzipped. Lazy-load via dynamic `import()` so `/vault` list view doesn't pay the cost. CSP `script-src 'self' 'nonce-{nonce}'` accepts the chunked load (Next.js webpack-runtime loader uses the same nonce); verify in Cypress that a fresh-tab `/credential/new` produces zero CSP-violation reports.

## Operator decisions surfaced (REQUIRED before `/gsd:execute-phase 4`)

The following six decisions have proposed defaults; operator must confirm OR override before executor runs.

1. **AAD label literal = `"sv:vault-credential:v1|"`**. Apex (NOT plural `vault-credentials`, NOT abbreviated `vc`); follows Phase-02 `sv:user-*:v1|` scheme exactly. Changing later is a data-migration event (every credential blob fails AEAD-unwrap). Confirm.
2. **Default password generator length = 20**, default char-classes = `{lower:true, upper:true, digits:true, symbols:true}`. 20 chars at 94-symbol alphabet ≈ 131 bits entropy — comfortably above 1Password's 128-bit anchor and zxcvbn-4 threshold. Confirm.
3. **Default passphrase word count = 5** (EFF large list, ≈ 64.6 bits). Default separator = `-`. 5 words is the EFF-recommended minimum for online-attack resistance; 6 for offline. Confirm — alternative is 6 (≈ 77.5 bits) at the cost of UX friction.
4. **Auto-lock idle = 15 min (900_000 ms), env `AUTO_LOCK_IDLE_MS`.** Reset triggers: `pointermove`, `keydown`, `visibilitychange` (resume from background), and a successful `/me` round-trip (i.e. tab is actively used). Choice: should `visibilitychange` (tab-hidden → tab-visible) RESET the timer, or should it START a tighter deadline (e.g. lock immediately on hide)? **Proposed default: reset on visible (treat as activity); start tighter deadline on hide is too aggressive for a 15-min cap.** Confirm.
5. **Favorites cap = unbounded in v1** (the flag is a single bool inside the encrypted blob; no server-side list to cap). UI sort puts favorites first, no max-favorites enforcement. Confirm.
6. **Reuse-detection scope = personal vault only (per REQ-VAULT-005).** Phase 07 (shared vaults) will need to decide: cross-vault detection (privacy concern: leaks "you reuse a password" across vault boundaries) vs per-vault. **Flagged for Phase 07 INDEX as an explicit decision.** Confirm Phase 04 default (per-vault).
7. **Version-rotation strategy = atomic CAS (`UPDATE … WHERE version = $current`); zero rows updated → 409 `CREDENTIAL_VERSION_CONFLICT`.** Alternative considered: optimistic merge (server attempts to JSON-merge two concurrent updates) — rejected because it would require server-side awareness of plaintext structure, violating Truth 7. Confirm — this is the load-bearing call that resolves REQ-VAULT-002's concurrency model.
