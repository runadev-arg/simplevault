# Local development setup

## Prerequisites

- Docker + Docker Compose v2 (`docker compose version` should print 2.x)
- Node 22 LTS (use `nvm use` or your installer's equivalent — `.nvmrc` pins this)
- pnpm 9.15+ (`corepack enable && corepack prepare pnpm@9.15.0 --activate`)

## Bring up the stack

```bash
git clone <repo> simplevault && cd simplevault
cp .env.example .env
pnpm install
docker compose up -d --build
```

Wait ~30 seconds for postgres + redis health to flip green:
```bash
docker compose ps
```

Smoke tests:
```bash
curl -s http://localhost:3001/health | jq
# Expected: {"status":"ok","db":"ok","redis":"ok","timestamp":"..."}

curl -sI http://localhost:3000/ | grep -i 'content-security-policy'
# Expected: header present with a 'nonce-...' value
```

## Daily dev workflow

Run apps in dev mode (with hot-reload), Postgres+Redis in docker:
```bash
docker compose up -d postgres redis
pnpm dev   # runs apps/api on :3001 and apps/web on :3000 with watch
```

## DB migrations

```bash
pnpm db:generate      # after schema change → produces SQL in packages/db/drizzle/
pnpm db:migrate       # apply pending migrations
pnpm db:studio        # open Drizzle Studio in browser
```

## Tear down

```bash
docker compose down           # stops, keeps volumes
docker compose down -v        # also wipes pg_data, redis_data — DESTRUCTIVE
```

## Troubleshooting

- **"Healthcheck unhealthy" on api**: usually means migrations failed. `docker compose logs api` will show the error.
- **PG 18.3 specific issues**: see [`.planning/phases/01-foundations/01-08-COMPAT.md`](../../.planning/phases/01-foundations/01-08-COMPAT.md).
- **Reset everything**: `docker compose down -v && pnpm clean && pnpm install && docker compose up -d --build`.

# Production deploy with Dokploy

This document is the operator runbook for deploying SimpleVault to a Dokploy-managed VPS at `pass.runadev.com`. Phase 01 makes the repo *deployable*; the actual go-live is owned by Phase 14.

## Prerequisites (operator)

- A Dokploy instance running on your VPS.
- A managed Postgres 18.3 instance in Dokploy (`pg_simplevault` or similar). You'll grab its connection string from the Dokploy UI.
- An A record for `pass.runadev.com` pointing at the VPS IP. Traefik (Dokploy) will provision Let's Encrypt automatically.
- (Later, Phase 02+) An SMTP provider (or self-hosted relay) for transactional email.

## One-time Dokploy setup

### 1. Create a new Redis service

Dokploy → Add Service → Redis. Name: `redis_simplevault`. Note the internal connection URL (e.g. `redis://redis_simplevault:6379`).

### 2. Create the API app

- **Name:** `simplevault-api`
- **Source:** Git (this repo)
- **Build type:** Dockerfile
- **Build context:** `.` (repo root — IMPORTANT: not `apps/api/`)
- **Dockerfile path:** `apps/api/Dockerfile`
- **Port (internal):** `3001`
- **Healthcheck:** `GET /health` (Dokploy honors the Dockerfile HEALTHCHECK — should be auto-detected)
- **Domain:** internal-only OR `api.pass.runadev.com` if you want it externally addressable for debugging. Recommend internal-only for prod.

### 3. Create the WEB app

- **Name:** `simplevault-web`
- **Source:** Git (same repo)
- **Build type:** Dockerfile
- **Build context:** `.`
- **Dockerfile path:** `apps/web/Dockerfile`
- **Port (internal):** `3000`
- **Domain:** `pass.runadev.com` (Dokploy provisions Let's Encrypt automatically)
- **Force HTTPS:** ON

### 4. Env vars (Dokploy encrypted env UI)

Set these on the **api** app:

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `3001` |
| `DATABASE_URL` | (from Dokploy Postgres service — copy from its details panel) |
| `REDIS_URL` | `redis://redis_simplevault:6379` |
| `JWT_SECRET` | `openssl rand -base64 48` (generate fresh; STORE OFFLINE TOO for disaster recovery) |
| `SERVER_CHAIN_SECRET` | `openssl rand -base64 48` (generate fresh; CRITICAL — losing this breaks audit chain) |
| `CORS_ORIGINS` | `https://pass.runadev.com` |
| `LOG_LEVEL` | `info` |

Set these on the **web** app:

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `3000` |
| `HOSTNAME` | `0.0.0.0` |
| `NEXT_PUBLIC_API_URL` | `https://pass.runadev.com/api` if you set up a Traefik route, OR the internal Dokploy network URL of api. Phase 12 will finalize. |

### 5. Networking

In Dokploy, ensure both apps + Postgres + Redis are on the same internal network. Postgres should NOT be exposed externally.

### 6. Deploy

Push to `main` → Dokploy auto-deploys (if you enabled auto-deploy on the app). Manual: hit "Deploy" in Dokploy UI.

The api's prestart hook runs `drizzle migrate` automatically; if migration fails the container exits and Dokploy marks the deploy failed (good — atomic).

## Verifying a deploy

```bash
curl -sI https://pass.runadev.com/ | grep -iE 'strict-transport|content-security'
curl -s https://pass.runadev.com/health    # if api is exposed
```

## Backups

See [`SECURITY-NOTES.md`](./SECURITY-NOTES.md) for the off-site `pg_dump → rsync` setup. Phase 14 wires this up for prod.

## Rollback

Dokploy keeps prior deploys; click "Redeploy previous version" in the UI. If a migration was applied that the previous version doesn't know about, rollback may require manual SQL — Phase 14 documents the expand/contract migration discipline that prevents this.
```

# Operator security responsibilities

These are things only YOU (the operator) can do. SimpleVault's security posture depends on them.

## Secrets you generate and own

| Secret | Where it lives | Disaster impact if lost |
|---|---|---|
| `JWT_SECRET` | Dokploy env (api) | Sessions invalidate; users re-login. Annoying, not catastrophic. |
| `SERVER_CHAIN_SECRET` | Dokploy env (api) | **AUDIT LOG VERIFICATION BREAKS** for all entries written under this secret. Critical. Always store an offline copy (encrypted USB / safe). |
| `Recovery Kit` (per-user, displayed in app) | User's responsibility | If user loses + forgets master pw → data loss. We can't help. |

Generate with: `openssl rand -base64 48`

## Off-site backups

The audit checkpoints + nightly `pg_dump` push to a separate VPS/NAS via rsync over SSH (Phase 14).

You need to provide BEFORE Phase 14:
- Target host (e.g. `backup.runadev.com`)
- Target user (e.g. `simplevault-backup`)
- Target path (e.g. `/var/backups/simplevault/`)
- A dedicated SSH keypair: private key in Dokploy secrets, public key in `~/.ssh/authorized_keys` of the target user
- The `authorized_keys` entry should restrict the key with `command="..."` (e.g. `rrsync -wo /var/backups/simplevault/`) so a compromise of the SimpleVault VPS cannot delete historical backups, only append new ones.

## Audit checkpoint git repo (Phase 10+)

Daily Ed25519-signed Merkle root of audit chain heads will be committed to a separate git repo (private GitHub or self-hosted Gitea). You need to:
- Create the repo
- Generate Ed25519 keypair (`ssh-keygen -t ed25519 -f audit-signing -C "simplevault-audit"`)
- Set the deploy key on the repo (write access)
- Store private key in Dokploy secrets

Decide repo location BEFORE Phase 10.

## SMTP (Phase 02+)

For invite emails, login alerts, vault sharing notifications. Pick a provider (Postmark / Mailgun / Mailjet) OR self-host (Postfix relay). Decide BEFORE Phase 02.

## Operator account 2FA

When you sign up your own SimpleVault account (you'll do this on first deploy), enroll BOTH a hardware WebAuthn key AND a TOTP backup. Don't be the operator who locked themselves out.

## Periodic operator tasks

- **Weekly:** review `pnpm audit` Dependabot PRs; merge or document defer.
- **Monthly:** run a backup-restore drill (restore latest `pg_dump` into a staging compose project; verify a known account's data integrity).
- **Quarterly:** rotate `JWT_SECRET`. Don't rotate `SERVER_CHAIN_SECRET` casually — it requires audit-chain ceremony documented in Phase 10.

## Detection signals

After Phase 10+, watch Grafana for:
- `audit_chain_breaks_total > 0` → DROP EVERYTHING and investigate.
- `twofa_bypass_total > 0` → bug in our 2FA enforcement → patch immediately.
- Sustained 5xx burst on auth endpoints → possible attack; check rate limiter config.
