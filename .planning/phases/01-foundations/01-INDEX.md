# Phase 01 — Foundations (Index + Wave Map)

**Goal (must be TRUE):** Operator can `pnpm install && docker compose up -d` locally and reach `http://localhost:3000` (web) + `http://localhost:3001/health` (api healthy, DB+Redis green). The same repo, when pushed to a Dokploy app pointing at `pass.runadev.com`, builds via the per-app Dockerfiles and starts. CI passes lint + typecheck + build + dep-audit on every push.

> **No production-deploy in this phase.** Phase 14 owns the actual `pass.runadev.com` go-live. This phase makes the repo *deployable*.

## Goal-backward truths

For the goal to be TRUE, all of the following must be observable:

1. `pnpm install` from a clean clone succeeds (no peer-dep warnings escalated to errors).
2. `pnpm build` from root builds every workspace (Turbo cache works).
3. `pnpm lint` and `pnpm typecheck` pass with zero errors.
4. `pnpm dev` starts both web (`:3000`) and api (`:3001`) concurrently.
5. `apps/web` renders a placeholder page with strict CSP + HSTS + other security headers — verified via `curl -I` showing the headers present.
6. `apps/api` exposes `GET /health` returning `{status: "ok", db: "ok", redis: "ok"}`.
7. `docker compose up -d` brings up postgres-18.3 + redis + api + web (postgres + redis NOT host-exposed); api applies the first Drizzle migration successfully against PG 18.3 via the Dockerfile prestart hook.
8. CI workflow on a fresh PR: green checks for lint, typecheck, build, `pnpm audit --audit-level=high`, container scan.
9. `packages/crypto` has its `exports` map configured for browser/node conditions (no implementation yet — just the type surface and module shape).
10. `packages/db` schema has a `users` stub table; the migration file generated by `drizzle-kit generate` runs cleanly against PG 18.3.
11. Operator runbook `docs/operator/DOKPLOY-DEPLOY.md` documents env vars + Dokploy build settings + domain config for `pass.runadev.com`.

## Key links (where this most likely breaks)

1. **PG 18.3 + Drizzle Kit compatibility** — bleeding-edge Postgres; if Drizzle's introspection or `pg` driver chokes, we either downgrade to PG 17 (operator action in Dokploy) or pin a workaround. Verified explicitly in Plan 08.
2. **`packages/crypto` exports map** — wrong conditional exports = browser bundle pulls Node crypto = silent failure or 100s of KB bloat. This is the load-bearing module for everything in Phase 02+.
3. **Next.js 15 middleware + per-request CSP nonce** — common pitfall: nonce must be generated before HTML render, propagated via header for next response, AND injected into all inline `<script>`/`<style>` tags. Strict CSP without `unsafe-inline` requires this exact dance.
4. **Docker network isolation** — postgres + redis MUST NOT have host port mappings. `backend` network must be `internal: true`. Easy to slip up by copy-pasting standard compose templates.
5. **Dockerfile prestart migration hook** — must be idempotent (re-runs on every container start are no-ops on already-applied migrations) and must FAIL the container if migration fails (no silent half-migrated state).

## Security gate (blocks completion of this phase)

Run via `/gsd:verify-work 1`:

| Auditor | What it must verify | Blocking? |
|---|---|---|
| `infra-deployment-auditor` | Docker hardening (non-root, read-only FS where possible, `cap_drop`, no host port mapping for postgres/redis, healthchecks, resource limits, security headers in app layer) | YES |
| `dependency-supply-chain-auditor` | `pnpm-lock.yaml` committed, `pnpm audit --audit-level=high` clean, no postinstall scripts in deps, no typosquats, dep tree size sane | YES |
| `threat-modeler` | Updates `.planning/security/THREAT-MODEL.md` with Milestone-0 baseline (full STRIDE skeleton + AT-1..AT-5 attack-tree drafts) | Informational (does not block, but must be updated) |

Phase 01 is **complete** when:
1. All 10 plans show ✅ in `STATE.md`.
2. All 11 goal-backward truths verified.
3. Both blocking auditors PASS in `.planning/security/AUDIT-LOG.md` with no Critical/High open in `FINDINGS.md`.
4. `threat-modeler` baseline committed.
